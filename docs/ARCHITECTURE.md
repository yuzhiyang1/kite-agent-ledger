# 架构与开发

## 调用流程

1. 调用方在付款前通过 `open` 登记受信的付款计划。业务生成稳定的 `run_id` 和 `call_id`。
2. 调用结束后通过 `capture` 写入 HTTP 结果与可选结算头。缺少响应时传两个 `null`。账本把原始结算头分类后丢弃。
3. `reconcile` 查询 Kite 测试网。交易未知时可在取得可信哈希后用 `attach` 补录。
4. `report` 返回每次调用和当前交易的最近核验。 `history` 列出所有核验结果，包括补录前的查询。

## 模块职责

- `model.py` 负责金额、地址、标识和 x402 v2 结算响应的边界校验。
- `chain.py` 负责只读 JSON-RPC、交易回执及 pieUSD 转账核验。RPC 请求只带链 ID 查询和交易哈希，端点来自操作方配置。
- `store.py` 事务性保存调用、HTTP 观察及追加式核验记录。相同调用输入可幂等重放，冲突返回明确错误。交易哈希使用 SQLite 唯一约束防止本地重复归因。
- `cli.py` 约束标准输入，把结果与错误输出给脚本。 `scripts/demo.py` 提供可运行的示例。

## 证据语义

- HTTP 状态回答服务如何响应。服务报告只能作为线索。在链上尚未找到交易、RPC 失败或没有哈希时，链上状态是 `unknown`。
- 只有官方测试网代币合约中存在恰好一条匹配付款方和收款方的转账、金额相符且回执成功，才返回 `confirmed`。核验结果附带区块和事件索引。
- `reverted` 表示提交用于核验的交易执行失败。 `mismatch` 表示交易存在，但没有提供匹配证据。两者只描述被查询的哈希。
- `manual` 表示由调用方另外取得哈希；账本不能据此证明该哈希确实来自那次 HTTP 响应。SQLite 是本地操作记录，数据库写权限决定记录是否可信。
- RPC 抛错或页面交付失败时，已有付款可能仍在处理。调用方应先核对已知证据再决定重试。

开发时按 [贡献说明](../CONTRIBUTING.md) 缩小改动范围，使用 [测试与部署](TESTING.md) 的检查命令。支付语义和 JSON 接口变更要一起更新相应测试和 [使用说明](USAGE.md)。
